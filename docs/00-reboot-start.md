# JDS 리부트 시작 문서

작성일: 2026-05-24
상태: 기존 구현을 버리고 새로 제작하기 위한 출발점

## 1. 목적

이 문서는 이전 JDS 저장소에서 **게임 컨셉만 보존**하고, 완전히 새로운 제작을 시작하기 위한 기준 문서다.

이전 구현은 참고 자료로만 취급한다. 코드 구조, UI 구현, 테스트, CSS, 씬 구성, 오버레이, 예제 파일은 그대로 가져오지 않는다. 새 프로젝트는 처음부터 다시 설계한다.

## 2. 한 줄 컨셉

**프로그래밍 버그가 몬스터가 된 세계에서, 플레이어가 개발 언어와 도구를 무기로 사용해 웨이브를 버티고 보스를 디버깅하는 터미널 IDE풍 생존 액션 게임.**

짧은 영문명 후보:

- Jiyoon Debug Survival
- JY Survival
- Debug Survival
- Runtime Survivor

## 3. 핵심 판타지

플레이어는 판타지 전사가 아니다. 플레이어는 망가진 개발 환경 안에 갇힌 개발자 또는 디버거다.

적은 고블린이나 좀비가 아니다. 적은 문법 오류, 런타임 에러, 의존성 충돌, 메모리 문제, 깨진 IDE 상태, AI 환각 같은 개발 문제다.

무기는 검이나 총이 아니다. 무기는 프로그래밍 언어, 프레임워크, 명령어, 개발 도구다.

플레이어가 느껴야 하는 감정은 다음과 같다.

- “나는 깨진 IDE 안에서 살아남고 있다.”
- “적 하나하나가 내가 아는 버그처럼 느껴진다.”
- “무기마다 프로그래밍 개념이 전투 방식으로 바뀐 느낌이 난다.”
- “스테이지 클리어는 압박 속에서 프로젝트를 디버깅해낸 것처럼 느껴진다.”

## 4. 목표 장르

주 장르:

- 2D 생존 액션
- Vampire Survivors류 웨이브 생존
- 자동 공격 무기
- 수동 이동과 위치 선정
- 시간 기반 이벤트와 보스전

보조 정체성:

- 코딩 테마 아케이드 게임
- 디버깅 패러디
- SSAFY / 개발자 스터디룸 분위기의 진행 구조
- 터미널 / IDE UI 판타지

## 5. 핵심 게임 루프

첫 플레이 가능 버전은 아래 루프에 집중한다.

1. 터미널 또는 IDE 스타일 시작 화면에서 게임을 시작한다.
2. 스테이지를 선택한다.
3. 시작 무기 하나를 선택한다.
4. 아레나에서 이동하며 계속 생성되는 적을 피한다.
5. 무기는 쿨타임에 따라 자동 발사된다.
6. 버그 몬스터를 처치하며 생존한다.
7. 일정 시간마다 특수 이벤트가 발생한다.
8. 생존 시간이 충분히 지나면 보스가 등장한다.
9. 보스를 처치하면 스테이지를 클리어한다.
10. 결과 화면에서 클리어, 실패, 해금 정보를 보여준다.

최소 루프 표어:

`무기 선택 -> 웨이브 생존 -> 디버그 이벤트 -> 보스 추적 -> 스테이지 클리어`

## 6. 최소 완성 게임 범위

첫 리빌드에서는 이전 기능을 전부 되살리려고 하지 않는다.

### 반드시 포함할 것

- 플레이 가능한 스테이지 1개
- 플레이어 캐릭터 1개
- 키보드 이동
- 시작 무기 3개
- 기본 적 3종
- 회복 또는 보조 역할의 적 1종
- 시간 기반 이벤트 1개
- 보스 1명
- 게임 오버 상태
- 스테이지 클리어 상태
- 간단한 HUD
  - HP
  - 타이머
  - 처치 수
  - 현재 무기
  - 이벤트 / 보스 상태

### 나중으로 미룰 것

- 여러 스테이지
- 도감 / 컬렉션 화면
- 메타 성장
- 복잡한 업그레이드 트리
- 다단계 보스 패턴
- 고급 적 패턴
- 비주얼 노벨식 스토리 대화
- 영구 저장 데이터

## 7. 첫 스테이지 방향

추천 첫 스테이지:

**Stage 1 - Python Basics**

테마:

- SSAFY 교실 터미널
- 초보 개발자의 첫 디버깅 생존 루트
- 고장 난 인터프리터와 기본 문법 오류

주요 적:

| 적 | 역할 | 설명 |
| --- | --- | --- |
| SyntaxError | 기본 추적 적 | 가장 기본적인 빨간 오류 몬스터 |
| NullPointer | 빠르고 약한 추적 적 | 빠르게 접근하지만 체력이 낮음 |
| SegFault | 느린 탱커 | 느리지만 체력과 접촉 피해가 높음 |
| HealBug | 도망치는 보조 적 | 처치하면 HP 회복 또는 회복 아이템 제공 |

스테이지 이벤트:

- `Indentation Panic`
- 일정 시간 후 들여쓰기 관련 적 또는 투사체가 몰려오는 이벤트

보스:

- `Jang Seonhyeong` 또는 다른 라이벌 / 디버그 보스
- 일정 생존 시간 후 등장
- 보스를 처치하면 스테이지 클리어

## 8. 무기 방향

무기는 프로그래밍 개념을 명확한 전투 방식으로 바꿔야 한다.

### 시작 무기

| 무기 | 전투 역할 | 컨셉 |
| --- | --- | --- |
| Python | 균형 잡힌 자동 조준 탄 | 초보자 친화적이고 안정적인 범위 대응 |
| C/C++ | 빠른 관통 직선 공격 | 포인터처럼 정밀하고 직접적인 디버깅 |
| Java | 방어형 궤도 무기 | 객체지향 보호막 / 근접 방어 |

### 추후 무기

| 무기 | 전투 역할 | 컨셉 |
| --- | --- | --- |
| Git | 되돌리기 / 기절 / 분기 공격 | branch, revert, merge |
| SQL | 무거운 범위 피해 | query, table drop, 군집 피해 |
| JavaScript | 불규칙 연속 공격 | async, event loop, callback |
| Django | 넓은 프레임워크 스윕 | request / response / template wave |
| Linux/Bash | 느리지만 강력한 명령 | sudo, purge, kill process |

## 9. 시각 방향

이 게임은 일반 판타지 아레나가 아니라 **플레이 가능한 디버거 / IDE**처럼 보여야 한다.

사용할 것:

- 어두운 터미널 배경
- IDE 패널 구조
- 네온 계열 문법 강조 색상
- 모노스페이스 폰트
- 오류 로그
- 짧은 글리치 효과
- 읽기 쉬운 범위 안의 CRT / 스캔라인 효과
- 작고 기능적인 HUD 패널

피할 것:

- 밝은 캐주얼 모바일 게임 스타일
- 중세 판타지 질감
- 플레이 상태를 가리는 장식 UI
- 위험, 피격, 보상, 타이밍을 전달하지 못하는 과한 이펙트

## 11. 리빌드 아키텍처 원칙

새 프로젝트는 처음부터 단순해야 한다.

권장 원칙:

- 여러 기능보다 하나의 수직 슬라이스를 먼저 만든다.
- 가능하면 게임 로직과 렌더링을 분리한다.
- 무기, 적, 스테이지, 이벤트는 타입이 있는 데이터 설정으로 관리한다.
- 각 모듈은 작고 책임이 분명해야 한다.
- Stage 1이 재미있어지기 전까지 미래용 추상화를 만들지 않는다.
- UI와 전투 가독성을 먼저 확보하고, 그 다음에 시각적 폴리시를 추가한다.
- 테스트는 모든 시각 요소가 아니라 순수 게임 로직 중심으로 작성한다.

권장 폴더 구조 초안:

```text
src/
  main.ts
  scenes/
    BootScene.ts
    MenuScene.ts
    GameScene.ts
  data/
    weapons.ts
    enemies.ts
    stages.ts
  systems/
    WeaponSystem.ts
    EnemySystem.ts
    EventSystem.ts
    CollisionSystem.ts
  ui/
    hud.ts
    screens.ts
  types/
    game.ts
```

이 구조는 출발점일 뿐이다. 엔진과 구현 방식이 결정되면 조정할 수 있다.

## 12. 첫 마일스톤

마일스톤 이름:

**M1 - 플레이 가능한 디버그 서바이벌 수직 슬라이스**

성공 기준:

- 시작 화면에서 Stage 1을 시작할 수 있다.
- 플레이어가 2D 아레나에서 이동할 수 있다.
- 적 최소 3종이 생성된다.
- 선택한 무기가 자동으로 발사된다.
- 적과 접촉하면 플레이어 HP가 감소한다.
- 적을 처치하면 처치 수가 증가한다.
- 시간 기반 이벤트가 적 압박을 변화시킨다.
- 일정 시간 후 보스가 등장한다.
- 플레이어는 죽거나 보스를 처치해 클리어할 수 있다.
- 게임 오버와 스테이지 클리어 화면이 작동한다.

완료 정의:

- 개발자 도구 없이 시작 화면부터 실패 또는 클리어까지 플레이할 수 있다.
- 임시 그래픽만 있어도 게임 컨셉이 알아볼 수 있다.
- 플레이테스트 후 일부 구조를 다시 고칠 수 있을 만큼 코드가 작고 단순하다.

## 15. 구현 전 결정해야 할 것

구현을 시작하기 전에 아래 결정을 내려야 한다.

- Phaser 3를 유지할 것인가, 다른 엔진을 선택할 것인가?
- 그래픽은 픽셀아트, 벡터 도형, UI 중심 추상 스타일 중 무엇으로 갈 것인가?
- 플레이어는 명시적으로 “지윤”인가, 아니면 일반 디버거 아바타인가?
- SSAFY references를 직접 유지할 것인가, 더 보편적인 개발자 학교 / 학습 공간으로 바꿀 것인가?
- Stage 1은 아케이드 생존 재미를 먼저 잡을 것인가, 학습 테마와 농담을 먼저 강조할 것인가?

권장 기본값:

- 빠른 리빌드를 위해 Phaser 3를 유지한다.
- 초기에는 벡터 / 절차적 임시 그래픽을 사용한다.
- 코딩 농담은 가볍고 읽기 쉽게 유지한다.
- 메타 성장보다 플레이 가능한 생존 루프를 우선한다.
